GEAAC · Engine Architecture

Layers

你看到的不是 Layer，是所有 Layer 的合成结果。这页建立 LayerStack 的 mental model：Application 怎么把一堆互不相识的模块编排成一帧，为什么同一个栈要按两个方向相反的遍历走两遍。

1主流程：Application 怎么编排一堆 Layer

Application 拥有一个 LayerStack。每一帧，它对这个栈做两趟方向相反的遍历：一趟更新（底 → 顶，全员执行），一趟派发事件（顶 → 底，抓到即停）。

2mental model：投影仪 + 透明片

Application

指挥 / 投影仪

拥有 LayerStack。每帧先 OnUpdate 全员，再对每个事件 OnEvent。不关心任何具体 Layer 是什么。

LayerStack

一张有序名单

std::vector<Layer*>。顺序 = 谁后加谁在上面 = 谁先收事件 = 谁最后画。

Layer

行为的贡献单元

每帧被 tick 一次、能收事件。常常（但不一定）产出视觉——纯逻辑层也合法。

Overlay

永远最顶

用胶水粘在栈顶。菜单栏、工具条、编辑器停靠。任何新 Layer 都盖不住它。

投影仪类比

一台投影仪，上面摞着一沓透明胶片。每个 Layer 就是一张胶片。最底是 3D 世界渲染，往上叠相机控制、Debug 面板，最顶是菜单栏。

每一帧，投影仪把整沓胶片从底到顶重画一遍。你看到的不是任何一张胶片，而是所有胶片叠加后的合成画面。有的胶片甚至不画任何东西——纯逻辑层只负责给别层喂数据。

输入则是另一回事：一根笔从最上面的胶片往下按。最上面那层说要这支笔（handled = true），底下就碰不到。菜单栏接住了鼠标点击，3D 场景就不会同时被点到。

核心修正：Layer 不是"你看到的东西"。单张胶片不是画面，它是画面的贡献者。这就是为什么它叫 layer（层）而不是 screen（屏）——它是被合成的原料，不是成品。

3两趟遍历：方向相反的两个 pass

这是 Layers 真正要内化的核心——同一个栈，每帧走两趟性质完全不同的遍历。

遍历 A · OnUpdate

全员参与，每帧都跑

for (Layer* l : m_Layers) l->OnUpdate(ts); 底 → 顶，每一个 Layer 都被 tick，没有短路，顺序通常无所谓。像乐队合奏——每个乐手每个小节都在演奏。

遍历 B · OnEvent

抓到即停，顶到底

for (auto it = m_Layers.rbegin(); it != m_Layers.rend(); ++it) 顶 → 底走，谁把 event.handled 设为 true，后面的 Layer 就再也看不见这个事件。

为什么不对称？更新的语义是"每个模块给这一帧做贡献"——所以人人有份；事件的语义是"这个输入被谁接管"——所以只给最先声明的人。前者是加法，后者是排他。

实用后果：栈顶的 Overlay（比如菜单栏）永远最先看到鼠标事件。菜单栏说"这是我点的"，底下的 3D 场景就不会同时被点到。这就是浏览器里"捕获段"的位置——只是这里只有捕获段，没有冒泡段。

4Layer vs Overlay：那条分界线

LayerStack 里只有一个 m_LayerInsertIndex 指针，把所有 Layer 和所有 Overlay 分隔开。

class LayerStack {
    std::vector<Layer*> m_Layers;
    unsigned int m_LayerInsertIndex = 0;
public:
    void PushLayer(Layer* layer) {
        m_Layers.emplace(m_Layers.begin() + m_LayerInsertIndex, layer);
        m_LayerInsertIndex++;      // 新 Layer 永远插在这条线上
    }
    void PushOverlay(Layer* overlay) {
        m_Layers.emplace_back(overlay);   // Overlay 永远 append 到末尾
    }
};

所以 vector 里永远是 [Layer1, Layer2, ..., Overlay1, Overlay2]——Overlay 永远排在 Layer 后面，也就是永远"更靠顶"、最后画、最先收事件。

LayerOverlay
插入方式插在 m_LayerInsertIndexappend 到 vector 末尾
谁更高后加的盖住先加的永远最顶，盖住所有 Layer
典型用途世界渲染、相机、游戏逻辑菜单栏、工具条、编辑器停靠
事件顺序收到没被上面接住的永远最先收到
会被新 PushLayer 盖住吗会不会

设计意图：Overlay 是"横切"的东西——ImGui 菜单栏和编辑器面板属于引擎本身，不该被任何游戏 Layer 盖住。Cherno 说这也是为什么 ImGui 面板要用 Overlay 而不是 Layer。

5和浏览器事件模型的对照

你的浏览器直觉有一半是对的——它确实有 propagate、有"谁先到谁说了算"。但它比 DOM 模型简单得多：

浏览器 DOMHazel LayerStack
结构树（祖先 - 后代）线性栈（邻居）
传播方向捕获下行 + 冒泡上行一趟：顶 → 底
停止传播stopPropagation()event.handled = true
遍历的是什么事件沿祖先链走事件沿名单走
Update没有对应概念全员每帧都跑

你之前的直觉"分捕获和冒泡两阶段"——在 LayerStack 里不成立。浏览器要两阶段是因为 DOM 是树：事件得从根走到目标、再走回来。LayerStack 是一列名单，不需要走回来，所以只有一趟。

6Layer 的接口：五个钩子 + 生命周期

这就是 Hazel 里 Layer 的全部契约。五个虚函数都是空的，留给具体 Layer 覆盖——Application 只认识这些钩子，不认识任何具体 Layer。

class Layer {
public:
    virtual ~Layer() = default;

    virtual void OnAttach() {}            // 挂上：注册资源、订阅事件
    virtual void OnDetach() {}            // 摘掉：释放资源、退订
    virtual void OnUpdate(TimeStep ts) {} // 每帧：游戏逻辑 + 渲染
    virtual void OnEvent(Event& e) {}     // 事件：谁先 handled 谁说了算
    virtual void OnImGuiRender() {}       // 编辑器面板（如果有 ImGui）
};

GEAAC 落地时先实现前四个钩子（onAttach / onDetach / onUpdate / onEvent），onImGuiRender 延后——沙箱的事件检查器是一个 pushOverlay 的观察者 layer（顶→底最先看到、从不 handled），不需要引擎侧画 ImGui。

  1. 1Application::PushLayer(layer) → 先 m_LayerStack.PushLayer(layer) 入栈，然后 Application 自己调 layer->OnAttach()。此时加载它需要的资源。OnAttach 是 Application 调——LayerStack 只是个数据结构。
  2. 2之后每一帧，Application 在遍历 A 里调 OnUpdate(ts)，更新这个模块的状态（可能顺带渲染）。
  3. 3每来一个事件，Application 在遍历 B 里把事件交给 OnEvent(e)。内部通常用 EventDispatcher 拆类型。
  4. 4如果启用了 ImGui，每帧还会调 OnImGuiRender() 画编辑器面板。GEAAC 暂不落地这个钩子（沙箱检查器用 React 直接渲染），等 ImGui-style editor slice 再加。
  5. 5弹出（PopLayer / PopOverlay）或应用析构时，LayerStack 对被移除的 Layer 调 OnDetach()——注意 OnDetach 的调用方在 LayerStack 这边，跟 OnAttach（Application 调）正好相反。

把 Layer 想成插头：推入即通电（OnAttach）、每帧运转（OnUpdate）、拔掉即断电（OnDetach）。LayerStack 是那个插座排，Application 是按下总开关的人。

7为什么这样设计：插件化组合

因为 Cherno 想让你能组合游戏，而不是写死一个巨型 Application。Application 只认识 LayerStack 的接口（Push / Pop / 遍历），它不 import 任何游戏代码。

加功能 = 改组装，不改 Application

想加一个物理模块？在 Sandbox 的 CreateApplication 里多 PushLayer(new PhysicsLayer)。想换相机手感？PopLayer 旧的再 push 新的。Application 一行不改。每个 Layer 是独立插件，只遵循"每帧 tick 我 + 把事件流给我"这个接口。

这正是你 Event Flow 那页"单通道流"的完整形态：Layer 是事件流的消费者，也是游戏逻辑的家。事件从 LayerStack.onEvent 一路顶→底到达（handled 截断），LayerStack 给了 Layer 位置和优先级。

这也是为什么 Cherno 让你在 Sandbox 里写 ExampleLayer：游戏代码全部长在 Layer 里。Layer 就是引擎和游戏之间的插件接缝。

8复习要点

一句话记忆：Application 拥有一个有序名单，每帧做两趟方向相反的遍历——更新从底到顶人人有份，事件从顶到底抓到即停。

复习 checklist

  • Layer 是"你看到的东西"吗？→ 不是。看到的是所有 Layer 的合成结果；Layer 是行为贡献单元，常常（但不一定）产出视觉
  • Layer 的钩子？→ OnAttach / OnDetach / OnUpdate / OnEvent（Hazel 还有第 5 个 OnImGuiRender，GEAAC 延后）
  • 谁调用 OnAttach？→ Application::PushLayer / PushOverlay；OnDetach 则由 LayerStack 在 Pop / 析构时调（不对称，别记反）
  • 每帧对栈做几趟遍历？→ 两趟：OnUpdate 全员底→顶；OnEvent 顶→底，handled 即停
  • 事件有"冒泡"吗？→ 没有。线性栈只有一趟顶→底，没有上行阶段
  • Layer vs Overlay？→ Overlay append 到末尾、永远最顶、最先收事件；Layer 插在 insert index，后加的盖先加的
  • 谁停住事件传递？→ event.handled = true（引擎内部的 stopPropagation）
  • 别和什么混？→ preventDefault（抑制浏览器默认动作）是 AppWindow 的事，跟引擎的 handled 是两码事——见 Window 事件桥梁 坑 5
