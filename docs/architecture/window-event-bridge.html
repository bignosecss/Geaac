Window 事件桥梁

DOM 里的原生事件，怎么变成引擎里干净的 Event，再被 EventBus 分发给订阅者。这页讲 TheCherno「Window Events」那一集移植到浏览器的核心：谁负责翻译、谁负责路由、谁负责消费。

1主流程：一条单向管道

整个系统是一根单向、一次性的管道：DOM → AppWindow → EventBus → 订阅者。依赖方向只有 AppWindow 同时认识 DOM 和引擎，其余每层只认识自己下游。

有两条独立的生产者管道：窗口输入（AppWindow）和主循环（AppTick / AppRender）。它们从不同源头 publish 到同一个 bus，订阅者不关心事件从哪条管道来。bus 是事件汇聚的中转站，不是 window 专属管道。

2mental model：四层 + 机场海关类比

DOM / Browser

外部世界

原始、杂乱：clientX/Y、e.code、deltaMode。只在这一层出现，绝不外泄。

AppWindow

桥梁 / 海关

唯一同时懂 DOM 和引擎的一层。翻译成引擎 Event，交给 sink。

EventBus

路由器

归 Application 所有。先 type 订阅、再 category 订阅，handled=true 即停。

Subscribers

消费端

Layer / 系统 / React hook。订阅感兴趣的 EventType，只讲引擎语。

机场类比

DOM 是机场外的世界。形形色色的入境者（原生事件）带着各自的杂七杂八行李进来——clientX/clientY、e.code、deltaMode，每个航班的格式都不一样。

AppWindow 是海关。唯一同时懂"外面"和"国内"的地方。负责把关、翻译，把每个人的信息整理成统一格式的护照（引擎 Event），然后放行入境。

EventBus 是国内的交通系统。把每个入境者送到对应的出口（订阅者）那里。handled 标志就像出口工作人员说"这个人我接了"，别人就不用再管。

订阅者是等在出口的人。只关心自己要接的那类人，到了就带走。

核心洞见：一旦入境，没人再关心你来自哪个航站楼、哪种飞机。下游所有人只讲引擎语。这就是那集真正教的东西——不是某个回调函数，而是"谁负责翻译、谁负责路由、谁负责消费"这种职责隔离。

3浏览器 ≠ GLFW：四个坑

GLFW 的回调是 1:1 的（窗口变了→resize 回调）。浏览器里 canvas 的尺寸归 CSS 管、没有"关闭"事件、按键重复只给布尔标志。以下四处，是移植时最容易想当然的地方。

坑 1 · Resize

不能用 window.resize

window.resize 只在视口变化时触发，canvas 本身被 CSS 改尺寸不会响。诚实的信号是 ResizeObserver 挂在 canvas 上，配合已有的 this.width / this.height 活取值。

坑 2 · Close

canvas 没有"关闭"事件

WindowCloseEvent 不该由某个 DOM 监听器产生，而应由宿主生命周期产生（比如 Application.close() 时发布一个），游戏逻辑借此存盘。

坑 3 · Key repeat

重复从"次数"变"布尔"

GLFW 给重复计数，DOM 只给 e.repeat 布尔。事件类的 repeatCount 期待数字，所以翻译成 e.repeat ? 1 : 0（或自己累计）。

坑 4 · Focus

canvas 不自动拿键盘

键盘监听挂在 canvas 上，而不是 window——canvas 才是游戏边界，页面其他 UI（输入框、未来的编辑器）的按键不该漏进游戏。引擎在 attach 时给 canvas 设 tabIndex={0} 使其可聚焦，宿主在游戏激活时 canvas.focus()。焦点在页面其他元素上时，游戏天然收不到键盘事件——这是对 GLFW"窗口抓全局输入"的有意偏离。鼠标留在 canvas 上——坐标本来就相对 canvas。

4翻译表：DOM → 引擎 Event

每个监听器都干一件"翻译"的事。事件类的字段——canvas-relative 坐标、platform keyCode、0=左键——本来就是留给这一步填的。

5设计骨架：attach(sink) + Application owns bus

当前代码库的状态：EventBus 和所有事件类已就绪，AppWindow 只是个 canvas 视图，Application 还没有 bus。 缺的正是中间那根线。

设计决策：Application 拥有 EventBus，AppWindow 提供一个 attach(sink) 把自己接进去。这正好是 ARCHITECTURE.md 里已经写的下一步（"Application owns the bus; browser input wiring (window/canvas listeners)"）。

// application.ts —— 构造时创建 bus，并把窗口接进去
export class Application {
  readonly events = new EventBus()

  constructor(config: ApplicationConfig) {
    this.window = config.window
    this.window.attach((event) => this.events.publish(event))
  }

  close(): void {
    this.window.detach()   // 卸载时摘掉 DOM 监听，防泄漏 / 双注册
    // ... 原有 rAF 清理
  }
}
// app-window.ts —— 窗口变成"事件生产者"
type EventSink = (event: Event) => void

export class AppWindow {
  private sink: EventSink | null = null

  attach(sink: EventSink): void {
    this.sink = sink
    this.canvas.addEventListener('keydown', this.onKeyDown)
    this.canvas.addEventListener('mousemove', this.onMouseMove)
    // ... wheel / mousedown / mouseup / ResizeObserver ...
  }

  detach(): void {
    // 反向 removeEventListener 全部
  }
}

为什么用 attach(sink) 而不是把 bus 直接塞给 window？

  1. 1保持"Application 拥有 bus"——窗口只拿一个 (event) => void 的最小接口，不知道也不关心谁在消费。对应 Hazel 的 SetEventCallback(std::bind(...))，只是 TS 里 EventBus 本身就是"回调注册表"，不需要 Hazel 那套单回调机制。
  2. 2好测试——sink 是纯函数接缝，测试可以喂一个假 sink 断言窗口翻译得对不对，不用真的建 bus。符合"每个 engine 模块带一个测试"的约定。

6追踪一条事件：鼠标移动

  1. 1用户移动鼠标，浏览器在 canvas 上触发 mousemove DOM 事件。
  2. 2AppWindow 的 onMouseMove 监听器（在 createApplication 时被 attach）触发。
  3. 3算坐标：rect = canvas.getBoundingClientRect()，x = e.clientX - rect.left、y = e.clientY - rect.top。
  4. 4new MouseMovedEvent(x, y) 构造完成。
  5. 5sink(event) → Application 的 (e) => this.events.publish(e)。
  6. 6EventBus.publish 先跑 MouseMoved 的 type 订阅者，再跑 Input | Mouse 的 category 订阅者；第一个设 handled = true 即短路。
  7. 7订阅者（相机控制器 / useEvent hook）拿到事件，更新游戏状态。

另一条独立管道是主循环：Application.tick() 每帧 publish(new AppTickEvent()) / publish(new AppRenderEvent())——这是 EventType 里 AppTick/AppRender 的归宿，由循环生产，跟窗口无关。两条管道在 EventBus 汇合。

7复习要点

一句话记忆：DOM 是外界的杂乱信号，AppWindow 是唯一的海关，EventBus 是国内分拣，订阅者是出口。依赖只有一条单向管道：DOM → AppWindow → bus → 订阅者。

复习 checklist

  • 谁拥有 bus？→ Application
  • 谁把 DOM 翻译成引擎事件？→ AppWindow（attach / detach）
  • 翻译时改了哪些字段？→ 坐标（减 rect.left/top）、repeatCount、button、delta
  • 四个浏览器坑都处理了吗？→ ResizeObserver / close 走生命周期 / repeat 布尔转数字 / canvas focus
  • 卸载时摘掉监听了吗？→ Application.close() 里 window.detach()，防 React StrictMode 双注册
